# Architecture

## Overview

    ┌────────────────────────────── App (SwiftUI) ──────────────────────────────┐
    │ RemoteView (Mac) / PhoneView (iPhone) ─ ZonePicker ─ InputPicker ─         │
    │ SettingsView ─ MenuBarView (Mac) ─ CloudSettings                           │
    │        │                                                                  │
    │   ReceiverStore (@Observable, @MainActor)                                 │
    │        │  optimistic "pending" overrides, zone names, discovery results   │
    └────────┼──────────────────────────────────────────────────────────────────┘
             │ Receiver protocol (Command in, AsyncStream<ReceiverState> out)
    ┌────────┴────────────── ReceiverKit (Swift package) ───────────────────────┐
    │ DenonReceiver (actor, NWConnection, port 23)                              │
    │ DemoReceiver (actor, in-memory receiver for demo mode)                    │
    │ DenonProtocol (pure encode/decode, unit tested)                           │
    │ Discovery (subnet probe for the control port)                             │
    └───────────────────────────────────────────────────────────────────────────┘

## ReceiverKit

- `Receiver` (protocol): `connect()`, `disconnect()`, `send(Command)`, `states: AsyncStream<ReceiverState>`. Anything brand-specific stays behind it; `inputs` and zones live in the state, not the protocol.
- `ReceiverState`: zones (`Zone`: power, volume, maxVolume, mute, input, `halfStep`), sound mode, bass/treble/sub, dynamic EQ, sleep minutes, `connected`, friendly name, and the receiver's source names / order / hidden set. `inputs` is derived: the enabled sources with the names configured on the amp.
- `Command`: brand-neutral enum (power, volume, step, mute, input, sound mode, tone, sub, dynamic EQ, sleep, refresh).
- `DenonProtocol`: `encode(Command) -> [String]` and `apply(line, to: &state)`. No I/O, so it is fully unit tested.
- `DenonReceiver`: actor over `NWConnection`. The receiver pushes status lines, so state is live without polling. Lines are split on `\r`. Commands are spaced 50 ms apart because AVRs drop faster input. Auto-reconnects with backoff (1s doubling to 10s). `.waiting` is treated as transient (Local Network permission can sit there) with a 15 s timeout.
- `DemoReceiver`: actor that keeps a simulated receiver in memory (two zones, five named inputs, sound mode, EQ, dynamic EQ, sleep) and applies every `Command` to it directly. Used by demo mode.
- Wire logging: `DenonReceiver` logs every line sent (`TX`) and received (`RX`) through `os.Logger` (subsystem `dev.antoine.SwiftDenon`, category `wire`).
- `Discovery.scan()`: enumerates the local /24 from `getifaddrs`, probes every host on port 23 in parallel, sends `PW?` + `NSFRN ?`, and accepts hosts that answer like an AVR (`PW`/`ZM`/`MV` lines). Reports the friendly name. No Bonjour name guessing.

## App

- `ReceiverStore` owns the connection, saved host (`UserDefaults`), local zone names, discovery results and web-UI availability. `start()` connects to the saved host, or scans and connects to the first receiver found. If the saved host fails three times it rescans (DHCP changes). Hosts may be `address` or `address:port`. With demo mode on (`demoMode` in `UserDefaults`), `start()` uses a `DemoReceiver` instead and leaves the saved host untouched.
- **Optimistic updates**: every setter calls `hold(key, matches:, apply:)`, which applies the change to local state immediately and registers a pending override. Incoming states pass through `reconcile`, which re-applies any override until the receiver confirms it (`matches`) or a timeout passes (1–1.5 s, 4 s for power). This prevents stale status lines from flickering the UI back.
- **Volume**: `setVolume` rounds to whole numbers unless the zone supports half steps and "Half-step volume" is on (the default; registered at launch). Sends are throttled to ~10/s; the final value is always sent.
- **Views**: `RemoteView` shows one of three states: connecting, standby (single large power button) or playing (volume, slider, ±, power/mute, input). `GlassControls.swift` has the glass button, the volume slider (thumb follows the pointer; the reported value snaps, and fast drags skip half steps) and the vertical EQ slider.
- **Settings**: a real window (a plain `Window` scene with id `settings`, opened from the gear with `openWindow`; a `Commands` group puts *Settings…* ⌘, in the app menu) rather than a sheet. It is not the `Settings` scene, which lays its toolbar out on a second row under the traffic lights, so the switcher sat lower than the traffic lights; a `Window` gets the same single-row bar as the remote. A sheet on macOS puts its confirm button in a bottom bar and ignores a top toolbar's centre item, so the page switcher could only ever be faked. In a window the switcher is a plain segmented `Picker` in the toolbar's principal slot, which the system draws as glass exactly like the zone picker in the main window, with the scroll-edge effect for free. The window uses the remote's `.ultraThinMaterial` container background so the toolbar glass sits on the same surface, and the picker is `fixedSize()` rather than given a width: a forced width left extra empty track at one end and uneven padding around the labels. The toolbar background stays at its default, since hiding it let scrolled content run under the traffic lights and switcher. No Done button; the window closes like any other. iOS still presents `SettingsView` as a sheet in a `NavigationStack`. Three pages:
  - **Amp**: receiver connection (switching, search, manual address, web-interface link), sound mode, dynamic EQ, sleep timer, EQ faders.
  - **Zones**: local zone names.
  - **General**: half-step volume, hide volume slider (− / + then sit either side of the number), arrow keys switch zones (swaps ←/→ and Tab), scroll to change volume, show in menu bar, hide it when away, demo mode, version.
- **Toolbar**: the principal slot always holds something (the zone picker, or a clear 200 pt spacer with its glass background hidden) so the gear stays on the right when there is only one zone or the receiver isn't connected. The picker is hidden while connecting, since the zone list is stale or unknown then.
- **Menu bar**: `MenuBarView` is a `MenuBarExtra` (window style) on the same `ReceiverStore`, so it controls whichever zone the main window has selected. It reuses `GlassSegmented` for zones (shaped like the toolbar's native picker), `GlassCircleButton`, `VolumeReadout` and `InputPicker`, has the same connecting/standby/playing states, is always sliderless (`−` number `+`, then input, mute and power on one row, then a glass *Open SwiftDenon* button), and handles ↑/↓, Space/M, P and Tab. The label is a template `NSImage` drawn by `MenuBarDial` (`MenuBarIcon.swift`) with the app icon's geometry: knob, indicator knocked out of it, 11 ticks over a 270° sweep, lit up to the indicator. Off or disconnected is a ring with all ticks dim; muted adds a slash. SwiftUI doesn't animate a menu bar label, so `MenuBarIconModel` watches the store with `Observations` and eases the drawn fraction toward each new volume over 0.35 s, redrawing every 16 ms. *Open SwiftDenon* (`AppWindows.showRemote`) activates the app and fronts the existing remote window (matched by the `WindowGroup` id `remote`), or calls `openWindow` if it was closed. `MenuBarExtra` has no second-menu API, so right-clicking (or control-clicking) the icon is caught by `MenuBarContextMenu` (`MenuBarMenu.swift`): a local `NSEvent` monitor for clicks whose window is the status item's, which pops up an `NSMenu` with Open, Settings…, Mute, Turn On/Off and Quit. SwiftUI only hands out `openWindow` inside views, so `MenuBarLabel` registers it with `AppWindows` when the label appears. `isInserted` is `showInMenuBar && (!hideMenuBarWhenAway || icon.reachable)`. `MenuBarIconModel.reachable` follows `store.state.connected`, but stays true for 10 s after a disconnect and at launch, so blips don't flicker the item. The binding's setter is deliberately empty: SwiftUI calls it with `false` every time the item is hidden, and writing that back overwrote the saved *Show in menu bar* preference, after which the item could never return.
- **iPhone** (`PhoneView.swift`): `RemoteView` is macOS-only; `RootView` in `SwiftDenonApp` picks one or the other. `PhoneView` is a `NavigationStack` over a mesh-gradient background, with the same states (connecting, standby, playing) and the same store. The zone switcher is `GlassSegmented` (the native segmented control on iPhone doesn't pad its labels evenly), in a toolbar item with its shared background hidden so it isn't glass on glass. `GlassCircleButton` applies `glassEffect` directly on iOS because the system glass button style wasn't showing its tint there. Settings is the same `SettingsView` in a sheet with a `NavigationStack`, Done at the trailing edge and the page switcher in the principal slot (the title must not be removed on iOS or the switcher disappears). Scene phase drives two things: `ReceiverStore.resume(awayFor:)` reconnects after more than 20 s in the background (or whenever disconnected), since iOS suspends the app and the socket dies silently; and the volume buttons are only captured while active, connected and the zone is on.
- **Volume buttons** (`VolumeButtons.swift`): iOS has no API for button presses, so `volumeButtons(enabled:onStep:)` watches `AVAudioSession.outputVolume` with KVO. It records the system volume, parks it at 0.5 (through the slider inside an off-screen `MPVolumeView`, which also keeps the system overlay from appearing), and treats any move away from 0.5 as a press: above is louder, below is quieter, then it resets to 0.5, ignoring the echo of its own reset. Each press is one `stepVolume(by: ±1)`. The original volume is restored when capture stops (setting off, app inactive, zone off). The session is `.ambient` with `mixWithOthers`, so other audio isn't interrupted. Setting `volumeButtons`, on by default. Not testable in the simulator.
- **Settings sync** (`CloudSettings.swift`): `CloudSettings` mirrors a fixed list of `UserDefaults` keys (`syncedKeys`, currently just `zoneNames`) with `NSUbiquitousKeyValueStore`. On start, what is in iCloud wins over the device's copy and anything only the device has is pushed up; afterwards it pushes on `UserDefaults.didChangeNotification` and pulls on `didChangeExternallyNotification`. A pull that changes something posts `.cloudSettingsDidChange`, which `ReceiverStore` uses to reload zone names. Values are compared before writing in both directions, so the two notifications can't loop. Only property-list values are supported, and a dictionary is replaced whole, so two devices editing different zones at the same moment would keep whichever wrote last. It needs the iCloud key-value entitlement (`Config/SwiftDenon.entitlements`, enabled by `CODE_SIGN_ENTITLEMENTS` in the git-ignored `project.local.yml`; see `project.local.example.yml`). **A free Personal Team can't sign with that entitlement**, so it is off by default; without it the store quietly keeps nothing and the app behaves as before. Not tested across two devices. **Adding a synced setting**: add its key to `syncedKeys`; if it is read through `@AppStorage` it updates by itself, otherwise reload it on `.cloudSettingsDidChange`. Planned: per-zone volume slider limits (a lowest and highest value). Device-specific behaviour (host, volume buttons, scroll volume, window frames) deliberately stays local.
- **Volume readout and slider**: `VolumeReadout` draws the number as one `Text` per digit, keyed by place value counted from the decimal point (`int1`, `int0`, `point`, `frac0`). Going from 9.5 to 10.0 therefore rolls the ones and tenths in place while a new tens digit scales in and the row eases back to centre, because a removed or inserted view leaves layout at once while its siblings animate. `GlassSlider` bounces the thumb to wherever the track was pressed (`.bouncy`), then follows the drag on a stiff `interactiveSpring` once the pointer moves more than 6 pt. `GlassSlider` has two drag modes. The Mac's is absolute (the bounce above). With `relative: true`, used on iPhone, touching the slider changes nothing: the thumb moves exactly as far as the finger, with no animation, wherever the finger started, and nothing is reported until it actually moves. `onEnd` receives the last value the drag reported rather than reading the current volume from the view: a fast tap can deliver the press and release before SwiftUI re-renders, and the old closure then re-sent the previous volume to the receiver, so the amp jumped to the new volume and straight back. In relative mode the finger's sideways movement is accumulated each event and multiplied by `scrubFactor(distance:)`, which depends on the finger's vertical distance from the slider's centre line, so the thumb no longer sits under a finger that has been scrubbing slowly. `GlassCircleButton(repeats: true)` (iPhone) replaces the `Button` with a zero-distance drag: the press fires once, then after 380 ms a task fires every 150 ms, shortening by 8 ms each step to 50 ms, until the finger lifts or moves more than 60 pt away. (SwiftUI's `buttonRepeatBehavior` was tried first and managed about two steps a second.) `PhoneView` handles one drag on the whole screen: sideways changes zone and a swipe up that starts in the bottom third opens the inputs, through `InputPicker`'s optional `isOpen` binding. The drag-position animation modifier must sit *inside* the value one: when both change in a single transaction the innermost `.animation(_:value:)` wins, and the other order silently gave an instant jump.
- **Scroll to change volume**: `scrollsVolume(_:)` (`ScrollVolume.swift`) puts a background `NSView` behind the volume number and slider (window and menu bar). It uses a local `NSEvent` scroll monitor and acts only on events inside its bounds, so it never blocks clicks. A wheel notch is one step, and every step that really changes the volume ticks the trackpad haptic; trackpad travel is accumulated at 8 points per step; momentum is swallowed; the final value is sent when the fingers lift (or on every event for devices that report no phases). Up is louder in either scroll direction setting. Off by default (`scrollChangesVolume`), because a stray scroll shouldn't raise the volume.
- **Reconnection**: `DenonReceiver` uses TCP keepalive (10 s idle, 5 s interval, 3 probes), treats end of stream or an error on the socket as a disconnect, and drops the connection when the network path stops being viable, then retries with backoff. `ReceiverStore.watchNetwork()` additionally restarts a disconnected connection one second after the network changes, so joining home Wi-Fi reconnects at once instead of after the backoff.
- **Shortcuts**: `Intents.swift` opens a short-lived connection to the saved receiver for power, volume, mute and input.

## Window sizing (macOS)

SwiftUI resizes windows instantly and imposes the content's minimum height, so height is owned by `WindowHeightAnimator`:

1. The content is laid out as an `overlay` of a flexible clear view, so it never constrains the window.
2. Each state view measures its own natural height (`onGeometryChange`) into a per-state dictionary. Per-state entries matter: a single shared value let a fading-out view overwrite the incoming view's height and clip the window.
3. The animator steps the frame with a timer (120 Hz, 0.35 s ease-in-out), top edge fixed, same easing in both directions. NSWindow's built-in animation was unreliable when shrinking.
4. The window is non-resizable and the zoom button is disabled; the default size is 380 pt wide so a fresh launch isn't 900 pt wide.

## Targets

macOS 26 / iOS 26 (Liquid Glass APIs), iPhone only on iOS (`TARGETED_DEVICE_FAMILY: 1`). The Xcode project is generated by XcodeGen from `project.yml` and is gitignored. `project.yml` includes an optional, git-ignored `project.local.yml` for per-machine settings (`DEVELOPMENT_TEAM`, and `CODE_SIGN_ENTITLEMENTS` for iCloud on paid teams; `project.local.example.yml` shows both), so no team ID is committed. Device builds need a signing team; simulator and unsigned Mac builds don't. `build/`, `build-*/` and `SwiftDenon.xcodeproj/` are ignored. `project.yml` declares the `SwiftDenon` scheme explicitly (XcodeGen stopped generating it implicitly).

## App icon

`App/AppIcon.icon` is an Icon Composer document added as a resource (`wrapper.icon`), with `ASSETCATALOG_COMPILER_APPICON_NAME = AppIcon`. Xcode compiles it into `AppIcon.icns` and `Assets.car`. If the Dock or Finder keeps showing the old icon after a build, that is the icon cache: re-register the app with `lsregister -f` and restart the Dock.
